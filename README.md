# Healthcare Appointment & Follow-up Manager

A clinic platform with separate patient, doctor, and admin experiences: patients book appointments and describe
symptoms in advance, doctors get an AI-generated pre-visit summary with an urgency level, post-visit notes are
turned into a patient-friendly summary with medication reminders, and both sides get email + Google Calendar
updates.

## Tech stack & why

- **Next.js 14 (App Router)** — a single deployable app: React frontend + API route handlers (`src/app/api/**`) in
  one codebase. Simplest thing that satisfies "Backend API, Frontend, Database" without standing up two separate
  services.
- **SQLite via Node's built-in `node:sqlite` module** (Node 22+, zero extra dependency) instead of Prisma/better-sqlite3.
  This was a deliberate call: the sandbox this project was built in blocks the binary-engine downloads Prisma needs
  and native-module prebuilds some SQLite drivers fetch, so a schema-first, dependency-free driver was the reliable
  choice. The schema itself (`src/db/schema.sql`) is plain SQL and would port to Postgres/MySQL with minimal changes
  if you outgrow SQLite — see [Deployment](#deployment) for notes on that.
- **Custom session auth** (bcrypt + a signed HS256 JWT in an httpOnly cookie, `src/lib/auth.ts`) instead of
  NextAuth — there's no third-party identity provider involved, so a small, auditable implementation was less
  code than wiring a full auth framework around a role model NextAuth doesn't natively express (patient/doctor/admin).
- **Anthropic API** for the two LLM features, with a deterministic rule-based fallback when no API key is present
  (see [LLM prompts](#llm-prompts)).
- **Nodemailer** for email, SMTP-compatible with any provider (SendGrid, Mailgun, Postmark, Gmail SMTP, Mailtrap…),
  with a console-logging "simulated" fallback when unconfigured.
- **googleapis** for Google Calendar OAuth2 + event CRUD, entirely optional per user.
- **node-cron** for the standalone worker process, with an HTTP-triggered twin for serverless deploys.

## Running without any external credentials

Every external integration degrades gracefully so the full flow (book → AI pre-visit summary → email → calendar →
post-visit summary → medication reminders) is demoable with **zero setup**:

- **No `ANTHROPIC_API_KEY`** → pre-visit and post-visit summaries are generated by a deterministic rule-based
  generator instead of a live model call. The UI labels these "Simulated" so it's obvious. `pre_visit_summary_status`
  / `post_visit_summary_status` is stored as `simulated` (vs `ready` for a real LLM response, or `failed` if a
  configured LLM call errored and the fallback was used instead).
- **No `SMTP_HOST`** → emails are logged to the server console instead of sent, prefixed `[SIMULATED EMAIL]`. The
  notification is still recorded in the `notifications` table with status `sent` (simulated success), so the whole
  notification history / admin screen works normally.
- **No `GOOGLE_CLIENT_ID`** → the "Connect Google Calendar" button never appears (status endpoint reports
  `configured: false`), and booking/cancellation simply skip calendar sync.

To see the *failure* path (not just the happy path) without a real outage, set `EMAIL_SIMULATE_FAILURE_RATE=0.5` in
`.env` — half of simulated sends will throw, and you can watch the retry/backoff and eventual `failed` status in
Admin → Notifications.

## Database schema

Full DDL: [`src/db/schema.sql`](./src/db/schema.sql). Applied automatically on first connection (`src/db/db.ts`) —
no separate migration step needed for this project's lifetime.

| Table | Purpose |
|---|---|
| `users` | All accounts (patient / doctor / admin) with bcrypt password hash. |
| `doctor_profiles` | One-to-one extension of a doctor `user`: specialisation, bio, slot duration, working hours (JSON per weekday). |
| `doctor_leave_days` | Individual dates a doctor is unavailable. Unique per `(doctor_id, leave_date)`. |
| `slot_holds` | Short-lived (5 min) exclusive hold on a `(doctor_id, slot_start)` while a patient fills the symptom form — see [system design write-up](./SYSTEM_DESIGN.md) for why this exists. |
| `appointments` | The booking itself, plus everything that accretes onto it: symptoms, AI pre-visit summary, doctor notes, prescription, AI post-visit summary, calendar event ids. |
| `notifications` | Every outbound email and its delivery lifecycle (pending → sent/failed, with attempt count and next retry time). |
| `medication_reminders` | One row per prescribed medicine; the worker fans these into `medication_reminder` notifications. |
| `calendar_connections` | Per-user Google OAuth2 tokens (absent = not connected). |
| `oauth_states` | One-time CSRF tokens for the OAuth2 redirect flow. |

Two constraints do the heavy lifting for correctness:

```sql
-- Only one confirmed/completed appointment can occupy a given slot.
CREATE UNIQUE INDEX uq_appointments_active_slot
  ON appointments(doctor_id, slot_start)
  WHERE status IN ('confirmed', 'completed');

-- Only one hold can exist on a given slot at a time.
UNIQUE (doctor_id, slot_start)  -- on slot_holds
```

## API reference

All routes are under `/api`. Authenticated routes read a `hc_session` httpOnly cookie (set by login/register);
there is no separate API token. Responses are JSON; errors are `{ "error": string, "code"?: string }` with an
appropriate HTTP status.

### Auth
| Method & path | Auth | Body | Notes |
|---|---|---|---|
| `POST /api/auth/register` | none | `{ name, email, password, phone? }` | Creates a **patient** account and logs in. |
| `POST /api/auth/login` | none | `{ email, password }` | Any role. |
| `POST /api/auth/logout` | any | — | Clears the session cookie. |
| `GET /api/auth/me` | any | — | Current user or `{ user: null }`. |

### Doctors & slots
| Method & path | Auth | Notes |
|---|---|---|
| `GET /api/doctors?specialisation=` | any | List/search doctors. |
| `GET /api/doctors/:id` | any | Single doctor profile. |
| `GET /api/doctors/:id/slots?date=YYYY-MM-DD` | any | Candidate slots for that clinic-local date, each tagged `available` / `booked` / `held`. |

### Admin: doctor & leave management
| Method & path | Auth | Body | Notes |
|---|---|---|---|
| `GET /api/admin/doctors` | admin | — | Full doctor list with contact info. |
| `POST /api/admin/doctors` | admin | `{ name, email, phone?, specialisation, bio?, slotDurationMinutes, workingHours, password? }` | Creates the doctor's user account + profile. Returns a generated `temporaryPassword` if none was supplied. |
| `PATCH /api/admin/doctors/:id` | admin | partial of the above | Update profile / hours / slot duration. |
| `GET /api/admin/doctors/:id/leave` | admin, doctor | — | List leave days. |
| `POST /api/admin/doctors/:id/leave` | admin | `{ date, reason? }` | Marks the date as leave; **cancels any existing confirmed appointments on that date and emails the affected patients** (see write-up). |
| `DELETE /api/admin/doctors/:id/leave?date=` | admin | — | Remove a leave day. |
| `GET /api/admin/notifications?status=` | admin | — | Notification log + status counts, for auditing delivery/retries/failures. |

### Appointments (booking flow)
| Method & path | Auth | Body | Notes |
|---|---|---|---|
| `POST /api/appointments/hold` | patient | `{ doctorId, slotStart, slotEnd }` | Step 1: place a 5-minute exclusive hold on a slot. `409 slot_unavailable` if already held/booked. |
| `POST /api/appointments/confirm` | patient | `{ holdId, symptomText }` | Step 2: convert the hold into a confirmed appointment, trigger the AI pre-visit summary, email both parties, sync calendars. |
| `GET /api/appointments` | any | — | Role-scoped list (patient: own; doctor: their schedule; admin: everyone). |
| `GET /api/appointments/:id` | any | — | Detail, with an ownership check for patient/doctor. |
| `POST /api/appointments/:id/cancel` | patient, doctor, admin | `{ reason? }` | Cancels, emails both parties, removes calendar events. |
| `POST /api/appointments/:id/post-visit` | doctor | `{ notes, prescription: [{ drug, dosage, frequency_per_day, duration_days, instructions? }] }` | Marks the appointment completed, generates the AI patient-friendly summary, creates medication reminders. |

### Medications & calendar
| Method & path | Auth | Notes |
|---|---|---|
| `GET /api/medications` | patient | Active medication reminders for the current patient. |
| `GET /api/calendar/status` | any | `{ configured, connected }`. |
| `GET /api/calendar/connect` | any | Returns the Google consent URL (`501` if not configured). |
| `GET /api/calendar/callback` | none (Google redirects here) | Exchanges the code, stores tokens, redirects to `/dashboard`. |
| `POST /api/calendar/disconnect` | any | Removes the stored connection. |

### Background worker
| Method & path | Auth | Notes |
|---|---|---|
| `POST /api/worker/tick` | `x-worker-secret` header if `WORKER_SECRET` is set | Runs one sweep: notification retries, medication reminders, 24h appointment reminders, expired-hold cleanup. See [Background jobs](#background-jobs). |

## LLM prompts

Both prompts are used verbatim as specified, in `src/lib/llm.ts`:

**Pre-visit summary** (system prompt enforces strict JSON output):
> Analyse these symptoms and return: urgency level (Low / Medium / High), chief complaint, and three suggested
> questions for the doctor. Symptoms: `<symptoms>`

Expected shape: `{"urgency_level": "Low"|"Medium"|"High", "chief_complaint": string, "suggested_questions": [string, string, string]}`.

**Post-visit summary**:
> Convert these clinical notes into a patient-friendly summary with medication schedule and follow-up steps: `<notes>`

Expected shape: `{"summary": string}`.

**Failure handling**: every call goes through a 15s timeout + one retry with backoff. If the provider errors, times
out, or returns something that fails schema validation, the request falls back to the same deterministic generator
used in simulated mode, the appointment's `*_summary_status` is set to `failed` with the error recorded in
`*_summary_error`, and the request **still succeeds** from the caller's perspective — a patient or doctor never sees
a broken booking because the LLM had a bad moment. The UI surfaces the distinction (`ready` vs `simulated` vs
`failed`) so it's never silently pretending a real analysis happened.

## Google Calendar setup

Calendar sync is fully optional; skip this section to run without it.

1. Go to the [Google Cloud Console](https://console.cloud.google.com/) → create a project (or pick an existing one).
2. **APIs & Services → Library** → enable the **Google Calendar API**.
3. **APIs & Services → OAuth consent screen** → configure it (External is fine for testing; add yourself as a test
   user if it stays in "Testing" status).
4. **APIs & Services → Credentials → Create Credentials → OAuth client ID** → Application type **Web application**.
5. Add an **Authorized redirect URI**: `http://localhost:3000/api/calendar/callback` for local dev, or
   `https://<your-domain>/api/calendar/callback` in production.
6. Copy the **Client ID** and **Client secret** into `.env`:
   ```
   GOOGLE_CLIENT_ID=...
   GOOGLE_CLIENT_SECRET=...
   GOOGLE_REDIRECT_URI=http://localhost:3000/api/calendar/callback
   ```
7. Restart the app. Logged-in patients/doctors will see a "Connect Google Calendar" card on their dashboard.

Each user connects independently (their own Google account, `calendar.events` scope only). On booking, an event is
created on each connected party's **primary** calendar; on cancellation, both events are deleted; access tokens are
refreshed automatically and the refreshed token is persisted.

## Email setup

Any SMTP-compatible provider works. Example for SendGrid:

```
SMTP_HOST=smtp.sendgrid.net
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=apikey
SMTP_PASS=<your SendGrid API key>
SMTP_FROM="Healthcare Clinic <no-reply@yourdomain.com>"
```

Mailgun, Postmark, Gmail SMTP (with an app password), and Mailtrap (for a safe testing inbox) all work the same way
— just their respective host/port/credentials.

## Background jobs

Two interchangeable ways to run the same sweep (`src/lib/workerJobs.ts`), covering: retrying due notifications,
sending medication reminders, sending 24h-ahead appointment reminders, and purging expired slot holds.

- **Persistent server** (Render, Railway, a VM, or `next start` on a box you control): run `npm run worker`
  alongside the web process. It uses `node-cron` internally (default every 2 minutes, `WORKER_CRON_SCHEDULE`).
- **Serverless** (Vercel etc., no long-lived process): point an external scheduler at
  `POST /api/worker/tick` every few minutes — Vercel Cron, a GitHub Actions scheduled workflow, or a free service
  like cron-job.org. Set `WORKER_SECRET` and send it as the `x-worker-secret` header so the endpoint can't be
  triggered by anyone who finds the URL.

## Deployment

The app is a standard Next.js app, so any of Vercel / Render / Railway work:

1. **Vercel**: import the repo, set the environment variables from `.env.example`, deploy. Because Vercel is
   serverless, also set up a Vercel Cron job hitting `POST /api/worker/tick` (with the `x-worker-secret` header) every
   2–5 minutes for reminders/retries to actually fire.
   > ⚠️ **SQLite caveat**: Vercel's filesystem is ephemeral/read-only outside `/tmp` between invocations, so the
   > SQLite file will not persist across deploys or even always across requests. For a real Vercel deployment,
   > point `DATABASE_FILE` at a mounted volume-backed path if your plan supports one, or port `src/db/schema.sql` to
   > a hosted Postgres and swap `src/db/db.ts` for a `pg` connection (the repository layer's SQL is close enough to
   > standard SQL that this is a bounded change, mostly the `strftime(...)` default timestamps and the SQLite-specific
   > partial `UNIQUE INDEX ... WHERE` syntax, which Postgres also supports natively).
2. **Render / Railway** (recommended for this project as-is): these give you a persistent disk and a persistent
   process, which is exactly what the SQLite file and the `npm run worker` background job want. Deploy the web
   service (`npm run build && npm run start`) and a second worker service (`npm run worker`) from the same repo,
   both pointed at the same `DATABASE_FILE` path on a shared/attached disk.

After deploying, run `npm run seed` once (e.g. via a one-off shell/job on the platform) to create the demo admin
account, then use the admin portal to add real doctors.

## Project structure

```
src/
  app/                    Next.js App Router pages + API routes
    api/                  Backend: auth, doctors, admin, appointments, medications, calendar, worker
    dashboard/            Patient / doctor / admin portal pages (role-aware)
  components/              Shared React components (Navbar, forms, UI kit)
  db/
    schema.sql             Full DDL
    db.ts                  node:sqlite connection + schema bootstrap + transaction helper
    repositories/          One file per entity: plain functions over prepared statements
  lib/
    auth.ts                 Sessions, password hashing
    booking.ts              Booking/cancel/leave/post-visit orchestration (the "business logic" layer)
    llm.ts                   Pre-visit / post-visit LLM calls + simulated fallback
    mailer.ts, notify.ts     Email transport + templated notification queue/retry
    googleCalendar.ts        Google OAuth2 + Calendar CRUD, all fail-soft
    slots.ts                 Working-hours → bookable-slot computation (timezone-aware)
    workerJobs.ts             The actual background sweep logic, shared by both worker entry points
  worker/index.ts            Standalone node-cron process
  types/                     Shared TypeScript types
```

See [`SYSTEM_DESIGN.md`](./SYSTEM_DESIGN.md) for the reasoning behind double-booking prevention, leave-conflict
handling, the slot-hold mechanism, and notification failure handling.
